# Redmi K40 样本 3.0.1-20260313：静态分析与 realme 对比

分析日期：**2026-11-09（UTC+8）**。分析／文稿：**Codex**。设备所有者提供样本并说明来源为 **Redmi K40、HyperOS 3、无 root**。具体 Android 版本、完整 ROM 构建号、原安装路径未提供；不把 compileSdk／targetSdk 或 HyperOS 名称当作实际运行 Android 版本。

**按设备所有者要求，本轮跳过 Redmi 日志提取与实机动态验证，仅分析已提供 APK。没有连接／读取 Redmi、安装应用、调用辅助 Binder 或发送新请求。** 2026-11-05 的真实缓存、流量、日志、合成 HTTP 测试与 root 卸载反馈均属于 realme 分析阶段，不能当成 Redmi 实测。

## 1. 最重要的变化

1. 申请的 17 项权限与组件声明没有新增／删除，业务 JSON 却增加了 Wi-Fi、行政区文本、eSIM 和应用事件统计。
2. DeviceInfo 新增 `BSSID`、`Esim`、`Frequency`、`InactiveEsimMNC`、`LinkSpeed`、`RSSI`；SigInfo 新增 `BSSID`、`District`、`SSID`；AppInfo 新增 `launchCount`。
3. `launchCount` 是事件类型 1 与 7 的累计，不是精确启动次数。`District` 拼接国家／省／市／区县，不能称为已证明上报门牌地址。
4. 签名换为 Xiaomi／MIUI 证书；经分别选择验证路径，v1、v2、v3 均验证通过。业务 RSA 公钥与两个定位 SO 则与旧样本逐字节相同。
5. 默认 URL、HTTP＋AES/RSA 格式、明文数据库缓存、后台周期与小米开机向导判断继续存在。以上均为代码和文件比较，不能证明 Redmi 已成功读取或发送这些新增字段。

## 3. Wi-Fi 字段：从 API 进入业务载荷

DeviceInfo：`f1.a.b(Context,e1.b)`（本地 JADX：`f1/a.java:219`），经 WifiManager.getConnectionInfo() 读取 BSSID、link speed、RSSI、frequency，写入 `e1.b` 的 H/I/J/K，最终由 `e1.b.b()` 写成 BSSID／LinkSpeed／RSSI／Frequency。这里 BSSID 是接入点标识，不是调用手机本机 MAC 的证据。

SigInfo：`e1.d.d(Context,int,g1.n)`（本地 JADX：`e1/d.java:314`） 读取 BSSID 与 SSID，写入 `g1.n` 的 J/K，由 `g1.n.a()`（本地 JADX：`g1/n.java:148`） 等位置序列化。该对象经定位回调写入 signal 表，后续 R 类型报文包含 SigInfo。因此新增的不只是 SDK 内部可能读取 Wi-Fi：**自有业务 JSON 已存在明确字段与赋值链**。

连接信息为空或 networkId=-1 时，代码写 NWC；不支持 Wi-Fi 时可能写 NW；异常会记录或保留默认值。Android 对位置敏感 Wi-Fi 信息还可能返回 UNKNOWN_SSID、占位 BSSID 或 networkId=-1，所以 NWC 不能独立证明实际上没有连接。实际读到有效 SSID／BSSID 需要 Redmi 权限／AppOps 与系统状态验证，本轮跳过。

参考：[Android WifiInfo](https://developer.android.com/reference/android/net/wifi/WifiInfo)。静态 API 调用不等于真实热点标识已采集或上传。

## 4. District：国家、省、市、区县文本

`GetSignalInfoReceiver.a.d(b1.c)`（本地 JADX：`com/mobiletools/systemhelper/control/GetSignalInfoReceiver.java:57`） 额外调用 `b1.c.k()/D()/h()/m()` 并拼接到 `g1.n.G`；`g1.n.a()`（本地 JADX：`g1/n.java:144`） 输出为 District。

沿 SDK 的地址 JSON 解析、`b1.a` 构造器和 getter 追踪，这四项对应 **country＋province＋city＋district**。代码没有在这一拼接中使用 street 或 street_number；不能只因字段叫 District 或 SDK 支持街道地址，就声称这里已上传详细门牌。

`GetSignalInfoReceiver.d(b1.b)`（本地 JADX：`com/mobiletools/systemhelper/control/GetSignalInfoReceiver.java:145`） → `b1.h.l(boolean)`（本地 JADX：`b1/h.java:285`） 将地址类型设为 all，新增了请求地址解析的设置；原 realme 的同名短方法 l(boolean) 只设置 altitude 标志，因此不能按混淆方法名直接比较含义。Redmi 同时调用 m(true) 请求 altitude；仍为 bd09ll、高精度、scanSpan=0，由外层闹钟触发。

地址解析可能失败或返回空／null 项，国家省市区县是否成功获取以及真实性未动态验证。旧 realme 报告的“未证实地址文本”只针对旧样本，本页是新版本静态能力变化。

## 5. launchCount：统计口径与调用链

`e1.f.b(UsageStatsManager,String)`（本地 JADX：`e1/f.java:85`） 使用同一约 24 小时窗口的 UsageStatsManager.queryEvents(begin,end)，逐包计数：事件类型 7 加一，事件类型 1 加一。结果经 g1.b.d(long) 存入成员，由 `g1.b.a()`（本地 JADX：`g1/b.java:65`） 以字符串写出。

Android 文档中 7 是 USER_INTERACTION，1 是 ACTIVITY_RESUMED／旧 MOVE_TO_FOREGROUND。用户交互和 Activity 恢复可能发生在同一次应用会话中，所以不能将它当作去重的冷启动次数、进程创建次数或用户点击次数。异常时方法捕获错误并返回已累计值，可能为零或部分统计。

原有前台时长 runTime、双卡和 Wi-Fi 流量字段继续存在，列表仍来自 UsageStats，安装应用列表用于补标签／UID；后续只按 com.android 前缀过滤，没有证据表明改成仅取某几个指定应用。

参考：[UsageEvents.Event](https://developer.android.com/reference/android/app/usage/UsageEvents.Event)。关键 1／7 分支还以 JADX fallback 的指令式输出复核，没有使用真实应用记录演示。

## 6. eSIM 与 HyperOS 版本读取

- `f1.a.d/e/l(Context,...)`（本地 JADX：`f1/a.java:262`）：依据 active SubscriptionInfo 的 isEmbedded()，生成两字符 Esim 状态；另有单 SIM／电话服务不可用等路径。设备标识排序时对该两字符顺序作相应交换。
- `f1.a.f(Context)`（本地 JADX：`f1/a.java:288`）：Android API >=34 的路径读取全部订阅与活动订阅，按 subscriptionId 求非活动集合，筛选 isEmbedded()，取 MCC＋MNC，以逗号连接输出 InactiveEsimMNC。不是在这一字段直接发送 ICCID／IMSI；也不代表设备一定支持 eSIM，或所有配置均可访问。
- `f1.m.j/w/x/y()`（本地 JADX：`f1/m.java:50`）：小米分支组合 ro.mi.os.version.incremental 与 persist.sys.xms.version／ro.mi.xms.version.incremental 等属性用于软件版本字段，处理 XMS 版本与 Beta 后缀。这里只能证实代码适配，不能反推出实际 ROM 构建号。

## 7. 未改变的主链与仍存在的问题

- 17 项请求权限、sharedUserId、组件 exported／permission／intent 声明与旧样本语义一致；**没有 Redmi 实际 grant 状态**。APK 不能单独证明它在原设备位于 priv-app 或获得平台权限。
- `f1.m.t(Context)`（本地 JADX：`f1/m.java:21`） 仍只检查 device_provisioned==1；该小米路径未读取 operator_service_improve_plan。vivo 额外同意开关判断继续存在，不能推广为所有品牌相同。
- DeviceInfo／AppInfo／SigInfo → JSON → 明文 dmregister／signal 缓存 → `e1.g.a(e1.b)`（本地 JADX：`e1/g.java:33`） → HTTP POST。g1.c/g1.j/g1.f 的主要加密与 HTTP 逻辑相同：MD5(JSON) 是 AES-128 密钥，AES/ECB/PKCS5Padding；RSA/ECB/PKCS1Padding 封装密钥；Content-Type 为 application/encrypted-json；sign 参数不是设备数字签名。
- 上传 RSA 证书仍为 UNICOM RSA-1024，与旧文件逐字节相同；默认地址仍为 `http://dm.wo.com.cn:18080/register`。Java URL 字面量集合均为 19 项（含一个模板），未发现增删；这不是运行时端点穷尽证明。
- dmregister 仍保存原始 JSON，失败／条件不符会缓存；历史取一条后先删再重发、R 取出 signal 后先清表再发的顺序继续存在。成功逻辑仍接受 200，并在外层把 416 当可接受；没有新增主业务响应指令解析。
- 采集默认 30 分钟、信号批量上报 12 小时、AppInfo／周期注册 24 小时；首次随机偏移和本地配置覆盖继续存在。不是本轮测得的实际执行频率。
- 辅助服务仍 exported=true、未绑定声明的 signature 权限；`RegisterHelperService.onBind(Intent)`（本地 JADX：`com/mobiletools/systemhelper/service/RegisterHelperService.java:56`） 返回配置 Binder。新 AIDL 把 enforceInterface 集中到事务范围检查，但 `service.a.AbstractBinderC0019a.onTransact(...)`（本地 JADX：`com/mobiletools/systemhelper/service/a.java:25`） 校验的是接口 token，不是调用者权限／签名。未见新增调用者鉴权，未做真实调用实验。
- SigInfo 的 BEARING 仍被写入 Mobile／WiFi／Disconnected 等网络状态，不能当运动方向；SPEED 的有效赋值未在这条业务采集链中确认。原有非联通标识部分掩码／基站摘要逻辑继续存在，但新设备上的实际值未核实，不能照搬 realme 的实机脱敏效果。
